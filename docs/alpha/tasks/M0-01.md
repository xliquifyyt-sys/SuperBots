# M0-01: Fix the 404 on load and stale Botpedia portraits

Browser smoke logs a 404 on the offline build; the audit found Botpedia portraits drawn before sprites load and stuck on the vector fallback.

## Acceptance
- [x] `node test/browser.mjs` (offline, :8123) prints `ERRORS none`.
- [x] Botpedia cards redraw after sprite loads; screenshot of Botpedia shows painted portraits for all 8 bots.
- [x] A new assertion in test/browser.mjs fails if any console 404 appears (append-only).

## Log
- 2026-10-14 client-ui: The 404 came from `GET /api/config` (and `/api/me`) in `src/ui/online.js` on a plain static server.
  `index.html` now ships `<meta name="superbots-host" content="static">`; `server/index.js` rewrites it to `server` when
  it serves index.html, and the client skips all `/api` calls on a static host (guest sign-in shows "Cannot reach the game server").
  Botpedia: `src/render/sprites.js` gains `onSpritesChange()` (every listener is kept, not only the first `loadSprites` caller);
  `src/main.js` portraits are `canvas.portrait` with `data-painted`, redrawn on each sprite arrival, DPR-aware, and the
  painted still is trimmed to its opaque bounds and fitted (it used to render at about a third of the card height).
  `test/browser.mjs` (append-only, +29 lines) fails on any console 404, and opens Botpedia at 390x844, 844x390 and 1280x720,
  requiring all 8 portraits to be painted. Gates run locally: determinism 6, rules, headless 20, features, bughunt 2,
  balance-gate 2, online, online-browser, browser (:8131) all exit 0; browser prints `ERRORS none` and
  `botpedia painted portraits <viewport> 8` for each viewport. Screenshots: test/shot-botpedia-*.png (gitignored).
